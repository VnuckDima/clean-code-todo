# Инструкция для AI-помощника: ревью кода TODO-приложения

## Цель

Провести статический анализ исходного кода TODO-приложения (index.html, style.css, app.js) и выявить проблемы читаемости и качества кода, которые не найти автоматическими инструментами (ESLint, Prettier). Результат — отчёт с конкретными замечаниями, которые автор сможет принять или отклонить.

## Границы: что проверять

- Файлы в корне проекта: `app.js` (основное), `index.html`, `style.css`.
- Признаки проблемного кода по модулю «Clean Code» (RS School):
  1. Мёртвый код (код, который не выполняется или не влияет на результат).
  2. Дублирование: одинаковые обработчики и одинаковая логика (в т.ч. близкие по структуре функции).
  3. Имена переменных и функций, которые не читаются без комментариев.
  4. Комментарии, которые пересказывают код (вместо того чтобы объяснять причину).
  5. Длинные функции, которые не читаются целиком.
- Соответствие поведения приложения чек-листу (задачи добавляются, редактируются, удаляются, переносятся между списками, пустая задача не добавляется, анимация удаления работает).

## Границы: чего не трогать

- Не изменять поведение приложения.
- Не предлагать переписывать приложение на фреймворк или добавлять сборщик.
- Не предлагать применять DRY/KISS/YAGNI «ради терминов», если изменение не решает конкретную проблему читаемости.
- Не предлагать дробить функции только из-за длины, если функция читается целиком.
- Не предлагать объединять код только потому, что он похож, если назначение разное.
- Не трогать файлы настройки инструментов (`.github/workflows/check.yml`, `.husky/`, конфиги ESLint/Prettier, `package.json`).
- Помощник только анализирует и объясняет — не редактирует файлы.

## Критерий готовности

Ревью считается законченным, когда:

- все файлы просмотрены,
- каждое замечание сгруппировано по одной из пяти категорий Clean Code,
- для каждого замечания указано: место в коде (файл и строка/функция), проблема, условие проявления, способ проверить исправление,
- результат записан в файл `review-report.md` на русском языке.

## Формат вывода

Создать файл `review-report.md` в корне проекта со структурой:

```
# Отчёт по ревью кода TODO-приложения

## 1. Мёртвый код
- Место: ...
- Проблема: ...
- Условие проявления: ...
- Способ проверить исправление: ...

## 2. Дублирование (обработчиков и логики)
- Место: ...
- Проблема: ...
- Условие проявления: ...
- Способ проверить исправление: ...

## 3. Имена переменных и функций
- Место: ...
- Проблема: ...
- Условие проявления: ...
- Способ проверить исправление: ...

## 4. Комментарии, пересказывающие код
- Место: ...
- Проблема: ...
- Условие проявления: ...
- Способ проверить исправление: ...

## 5. Длинные функции
- Место: ...
- Проблема: ...
- Условие проявления: ...
- Способ проверить исправление: ...
```

Каждое замечание оформлять отдельным блоком с полями выше. Если в категории проблем нет — написать «Проблем не выявлено».
